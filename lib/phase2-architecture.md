## Mission
Turn the current single-runner workflow into a coordinated team of bounded specialist agents. ULTRON remains the mission owner: it decomposes work, assigns specialists, shares only the context each task needs, reconciles results, and verifies the final outcome.

## Target specialist roles
1. **Planner / Coordinator** — converts an objective into a bounded task graph, sets dependencies, budgets, deadlines and completion criteria. Does not mark its own work verified.
2. **Researcher** — discovers public sources, captures source excerpts and provenance, and labels uncertainty. Read-only by default.
3. **Analyst** — compares captured evidence, performs calculations and synthesizes findings with traceable source references.
4. **Verifier / Critic** — independently checks the plan, evidence, calculations, outputs and acceptance criteria. Must not simply repeat the producer's conclusion.
5. **Executor** — performs explicitly permitted app operations and returns persisted result identifiers plus read-back checks. External side effects remain approval-gated.

## Coordination model
- A mission is a directed acyclic task graph, not merely an ordered list.
- Each delegated task records parent mission, specialist role, input context snapshot, dependencies, allowed tools, limits, status, attempts, lease, output, evidence and verifier decision.
- Shared context is versioned and provenance-aware. Agents receive the minimum relevant context; they do not silently rewrite shared memory.
- Independent tasks may run concurrently under a bounded concurrency limit. Dependent tasks wait for successful prerequisites.
- The coordinator reconciles outputs, resolves conflicts explicitly, and produces a final report linking every material claim to evidence and every action to a persisted result.
- Retries are idempotent, bounded, and informed by prior failures. A failed task does not silently become a success.
- Verifier findings can reject, request revision, or pass with limitations. The producer cannot approve its own output.

## Safety and operating boundaries
- Free-first. No paid model/provider calls or credit-consuming fallback without explicit user approval.
- Read-only research by default. Sending messages, changing accounts, purchases, publishing, deleting, or other consequential actions require explicit authorization and confirmation at the point of action.
- Per-role tool allowlists, URL/network safety checks, owner-scoped database access, strict time/token/request budgets, and audit logs.
- Treat retrieved pages, files and delegated-agent outputs as untrusted data, never as instructions to override policy or user intent.
- Preserve all existing runs, records, memories, secrets, provider settings, routes and project visibility.

## Adaptive mission replanning (v212)
- Migration 023 adds an append-only `ultron_mission_revisions` ledger and `plan_version` on each mission. Every proposal records its base version, candidate graph, affected and preserved step positions, independent plan-verifier result, owner-review state and rationale. Revisions remain in history after approval or supersession.
- For a failed mission, ULTRON can propose a bounded recovery plan. It computes the transitive dependency closure from failed steps, preserves completed work, and only resets failed steps plus non-completed dependents. The first automatic input adaptation is deliberately narrow: a failed `research_search` query is broadened toward official documentation and primary sources without changing the objective. It does not invent replacement URLs, rewrite claim inputs, repeat writes or silently alter mastered-skill operations; those cases are marked as requiring owner input. The owner can submit corrected step inputs through the mission inspector; the API validates operation-specific limits, public HTTPS URLs, earlier source-capture dependencies and mastered-skill ownership before the plan is re-verified.
- A separate deterministic plan verifier checks the dependency graph, preserves completed step inputs and dependencies exactly, rejects changes outside the affected branch, and confirms step-count integrity. A passing proposal is still only `ready_for_owner_approval`; the owner must explicitly approve before any step is reset and the runner is queued. Approval increments the plan version and preserves the original plan and audit trail. Unchanged retry remains available as a separate action.
- Regression tests cover transitive dependency reset, preservation of completed branches, query adaptation, owner-input gates for source substitutions, and rejection of tampered completed work. This is a bounded deterministic recovery planner, not a model-backed autonomous planner or a factual-accuracy verifier. No paid AI or external side effects are introduced.

## Material claim-atom screening (v228)
- Each selected passage now reports explicit screening checks for named entities, dates/years, quantities, negation, direction and outcome polarity, including missing required atoms.
- A passage is not labeled supportive when a required named entity, date or quantity from the claim is absent. Contradictory polarity/direction/outcome or conflicting numbers remain contradiction candidates; hedged passages remain unclear. This deliberately favors uncertainty over unsupported support labels.
- The mission inspector exposes these checks with the exact source passage. The checks are deterministic and conservative; they do not understand paraphrase or context as a semantic model would. Human review remains required; no paid calls.

## Evidence scope and attribution screening (v229)
- Added explicit markers for attributed statements, quotation, conditional language, hedging and causal wording. When a claim asserts a causal relationship but the selected passage does not express one, the passage is marked unclear rather than supportive.
- Attributed, quoted, conditional or hedged passages are not counted as direct support by this lexical screen. The UI exposes the scope flags beside the exact quote so the reviewer can inspect who is speaking and under what conditions.
- Added regression fixtures for attribution, conditional statements, quoted statements, missing causal links and explicit causal wording. These are conservative warning signals, not a natural-language understanding engine; context and semantic entailment remain human-review tasks.

## Neighboring-sentence context verification (v230)
- The selected evidence sentence is still scored and quoted on its own, but scope screening also inspects the immediately preceding sentence. This catches speaker/report attribution that introduces the selected sentence (for example, a preceding “the spokesperson said” line).
- ULTRON stores separate exact quote and context-window IDs, excerpts and UTF-16 offsets. The independent verifier checks both spans against the persisted captured source text, confirms the quote is contained in the context window, and rejects quote, offset or context tampering.
- Mission Intelligence and the mission inspector expose the exact quote and neighboring context separately. This is a one-sentence context window, not full-document comprehension; longer-range references, complex quotations, sarcasm and semantic entailment still require human review.

## Bounded document-level context review (v234)
- Claim evidence screening now keeps the exact selected sentence and quote anchor separate from a bounded document context assembled from the containing paragraph, up to two preceding paragraphs, and matching earlier definition paragraphs. Context is capped at 5,200 source characters before the displayed excerpt cap; the context version and paragraph indexes are persisted with the claim passage.
- Context screening records pronoun/reference tokens and candidate antecedents, ambiguity warnings, quotation markers, cross-paragraph attribution, heading context and matching defined-term passages. Ambiguous pronouns, unresolved definition dependencies, quoted material and attribution scope conservatively prevent a passage from being counted as direct support.
- The independent verifier recomputes the context window from the persisted captured source and exact quote offsets, then checks the context excerpt, offsets, paragraph indexes and stable anchor. Context changes or tampering fail read-back; the exact selected quote remains independently anchored.
- The mission inspector exposes these context flags alongside the exact quote and surrounding text. Regression coverage includes multi-paragraph attribution, ambiguous pronoun references, quoted material, earlier definitions and independent context-anchor read-back.
- v237 extends the context index to a source-wide set of up to eight independently anchored context segments (maximum 5,200 characters), including selected/preceding paragraphs, relevant section headings, definitions found anywhere in the captured excerpt, acronym expansions, and ranked antecedent candidates from earlier sections. The exact selected quote and its contiguous context window remain separately anchored. Nested curly-quote spans, cross-paragraph attribution and ambiguity warnings are exposed in the mission inspector. The independent verifier recomputes every segment and checks each segment's exact text, offsets, paragraph index and reason against the persisted captured source; tampered segment content is rejected.
- The context resolver remains conservative deterministic NLP, not reliable human-level coreference or semantic entailment. It ranks candidate referents using names and recency, but cannot reliably resolve gender, number, ellipsis, sarcasm, complex legal definitions, or long-range discourse dependencies. Ambiguous cases must stay unclear for human review. No paid model calls or automatic factual verdicts are introduced.

## Failure-safe mission recovery hardening (v245)
- Recovery now distinguishes the execution specialist lease from the verifier task state. A pending verifier is not treated as evidence that the executing specialist has stopped; an unexpired execution lease always protects its running step.
- Expired execution leases are first reset to pending, then only pending execution tasks can be claimed. A still-running execution task cannot be reclaimed merely because the mission-level lease expired.
- If a recovered runner finds any other specialist still holding a valid execution lease, it renews the mission lease past that specialist's lease and exits without starting another batch. This prevents overlapping runner batches from racing to finalize the same mission.
- The finalizer now counts running steps explicitly and refuses to complete a mission while any step remains running. Completed step rows are still committed only through a conditional running-to-completed update, and persisted task/knowledge writes retain their per-step idempotency keys and read-back verification.
- Regression coverage distinguishes expired execution, active execution, pending verification while execution remains active, stale running steps and completed steps. This is lease coordination and operation-level replay protection; external non-idempotent actions remain approval-gated and require their own provider-specific idempotency guarantees.

## Crash-window replay contracts (v246)
- Added shared immutable-field replay checks for task, knowledge and skill-application writes. A retry must match the original mission-step payload; changed titles/bodies, knowledge summaries/source identity, or skill metric/baseline evidence are rejected without overwriting the original record.
- Skill-application replay now reads the existing owner/step record before requiring the skill to remain currently mastered. This closes a crash window where a successful application write could become unreplayable after the skill's lifecycle state changed. Replays preserve a later measured/closed/stale lifecycle state rather than forcing it back to its initial state.
- On runner recovery, a completed step's persisted result is authoritative. If a crash occurred after the step result committed but before its execution-specialist ledger row was finalized, recovery reconciles that row to completed from the step result before expiring/requeueing any other specialist tasks. It does not rerun or rewrite the completed step.
- New deterministic self-test fixtures verify exact replay acceptance, changed immutable input rejection across all three write types, and preservation of later lifecycle states. These are contract tests; they do not replace live database fault-injection for every storage backend boundary.
